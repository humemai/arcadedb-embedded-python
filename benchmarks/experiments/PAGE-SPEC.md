# Project page spec: what the page contains and what each cell must satisfy

The DBBench page at `humem.ai/research/dbbench` is the PRIMARY artifact: its lane pages render the tables of `results/web_benchmarks.json`, which holds rows of the 2026-11 instrument only. A paper, when there is one, is written from the same frozen rows at a stable release (DECISIONS #42); this file governs what the page shows. This file is the contract: what tables exist, what rows and columns they carry, which figures are published, and what a cell must satisfy to be printed.

`PROTOCOL.md` says how a number is produced. `FAIRNESS.md` says when two numbers may be compared. This file says what gets shown. If they disagree, PROTOCOL wins on production and FAIRNESS wins on comparison; this file never licenses a cell those two would refuse.

---

## 0. The rules every published cell obeys

1. **Serial, full cpuset.** Every published latency, throughput, percentile, and memory cell runs one at a time on mini's `cpuset 0-11` (the 12 P-core THREADS on 6 physical P-cores; see 0a), `workers=1`, `tier=paper`. Parallel shards exist for sweeps and exploration only and may never reach the page. Enforced: `runner.py` refuses `workers != 1` at paper tier; `load_canonical` drops partial cpusets.
2. **N=5, median [min-max].** Five repetitions per cell, reached in two passes (PROTOCOL.md section 1). Any table with a cell below n=5 states its n in a condition, and no page sentence may assert an n that a cell it covers does not meet. Per-table operation and repetition counts are generated conditions (`export_web._counts_note`), never typed.
3. **One engine commit per table.** Every ArcadeDB row in one table comes from the same upstream commit, stamped as `engine_commit`; the native and JVM builds of one release are two arms built from that one commit (section 1). Comparators are digest-pinned images. See section 1. Enforced at production time: `runner.py` refuses a paper-tier ArcadeDB run when `ARCADEDB_ENGINE_COMMIT` is unset, before any cell starts, and `bench_common.run_conditions()` reads it so bespoke probes carry it too. A rule the page depends on may not be a printed reminder to a human.
4. **One corpus per table.** Every row in a table describes the same dataset at the same size. A table whose rows disagree on `n_docs` (or the lane's size field) is a defect, not a comparison. The fingerprint must come from the corpus the lane loaded, not from a module constant (`l2_graph.py` and `l3_sparse.py` point it at the loaded data; BUGS.md F6 is the sparse lane running the synthetic corpus under a paper label).
5. **A knob the campaign sets must reach the cell, be honoured by the lane, and resolve inside the container.** `runner.py`'s env passthrough is a CLOSED tuple: a knob absent from it silently runs the in-script default. Three checks, each of which has failed once: DELIVERED (diff every lane's `environ.get("UPPER_CASE")` against what the runner passes), HONOURED (an unknown mode is a hard error, not a silent fallback to a literal default), and RESOLVED where the process runs (the mount is printed in the preamble and a missing corpus is refused on the host). Run the delivery diff whenever a lane gains a knob.
6. **The config PROFILE is recorded on every row.** ArcadeDB ships profiles that rewrite defaults wholesale: one sets `VECTOR_INDEX_GRAPH_BUILD_CACHE_SIZE=-1` with both cache heap percentages at 50, another pins both caches to a flat 10,000, against a default of `graphBuildCacheSize=0` (auto) and `graphBuildCacheMaxHeapPercent=25`. The profile can move a build several-fold on its own, so two rows under different profiles are not comparable. The percentage applies only on the AUTO path; quoting it for a run that pinned an absolute cache size is wrong.
7. **A probe must measure the thing its column is named after, and a bespoke stage must not hardcode a condition the lane derives.** A read that costs about as much as an empty query did not reach the structure, and a write whose index-entry count does not move did not land; assert both in the lane rather than trusting the query text (the `graph_gav` read once ran in SQL, which cannot reach a Graph Analytical View, and the sparse read was a `count(*)` that never touched the index). A stage that sets by hand any condition the lane computes (heap, cpuset, tier) has to say so on the row, and a comparison spanning stages has to check that the conditions match. The lifecycle `graph_gav` situation is withheld (`export_web.LIFECYCLE_WITHHELD`) because its corrected read changed scope; what it needs before it can print is CAMPAIGN.md section 7, row 34.

## 0a. The machine

Every published number is measured on **mini**. The laptop is a development host: it compiles, it runs probes, and nothing it produces reaches the page.

| | mini (bench host) | laptop (dev only) |
|---|---|---|
| CPU | 12th Gen Intel Core i9-12900HK | Intel Core Ultra X9 388H |
| topology | 1 socket, 14 cores, 20 threads: 6 P-cores with SMT (12 threads) + 8 E-cores | 16 cores, 16 threads, no SMT |
| `cpuset 0-11` | the 12 P-core threads, verified by max frequency: cpu0-11 report 4900 MHz, cpu12-19 report 3800 MHz | **NOT the P-cores here.** The kernel reports `cpu_core = 0-3`, `cpu_atom = 4-15`, and max frequency agrees: cpu0-3 at 5100-5200 MHz, cpu4-11 at 4000, cpu12-15 at 3700. `0-11` on this machine is 4 P + 8 E, mixed. Laptop probes pin `0-3`. |
| RAM | 64 GiB installed (61.3 GiB usable) | 30 GiB |
| storage | Samsung SSD 980 PRO 2 TB NVMe (root, `/home`, `/var/tmp`, all bench data) | Samsung MZVL22T0HDLB 1.9 TB NVMe |
| OS / kernel | Ubuntu 26.04 LTS, 7.0.0-30-generic | Ubuntu 26.04 LTS, 7.0.0-29-generic |
| Docker | 29.7.2 | |

Four things about that table are load-bearing and must be said on the page, not just recorded here.

**`cpuset 0-11` is 12 THREADS on 6 PHYSICAL CORES, not 12 cores.** SMT is on (`/sys/devices/system/cpu/smt/control` = `on`). A reader who assumes 12 physical cores will over-estimate what a parallel build had available, and every "12-core" phrasing in our own prose is wrong.

**`cpuset 0-11` means something DIFFERENT on the two machines.** On mini it is the P-core threads. On the laptop the kernel says `cpu_core = 0-3` and `cpu_atom = 4-15`, so the same string selects 4 P-cores plus 8 E-cores. Laptop probes pin `0-3`; anything published re-runs on mini anyway, so the two never need to mean the same thing, only to be stated.

**Frequency is not pinned.** The governor is `powersave`. The 2026-11 pass runs with turbo OFF (`intel_pstate/no_turbo` = 1, set on the bench host 2026-10-24; a timed stage refuses to start with it on), so the P-cores top out at 2.5 GHz, and the clock below that cap still varies with load and heat: a long build and a short query do not see the same clock. The passes before 2026-10-24 ran with turbo ENABLED (`no_turbo` = 0, busy cores at 4.3 GHz). This is a mobile-class part in a small chassis, so sustained all-core work throttles in a way a server part would not. It is why every published number runs SERIAL: co-scheduling on this host does not merely add noise, it changes the clock the other cell sees.

**CPU idle states are held off for the length of a timed cell.** The host runs with the `intel_idle` driver and every sleep state enabled, down to C10 (exit latencies of 170 to 230 microseconds for C6, C8, and C10), and a single-client time under a millisecond could include the cores' wake-up latency. Under the 2026-11 instrument the runner holds the cores out of their deep idle states for the length of a timed cell, at a target of 10 microseconds (C1E stays allowed, C6 and deeper do not; PROTOCOL.md section 7), and every row records `cpu_dma_latency_us` and `cpu_dma_latency_held`; the page says what was held in one plain sentence in its setup block (DECISIONS #177).

Under a long build the package bounces off its thermal ceiling (BUGS.md F45). The power mode stays as the machine ships, because pinning the clock would lower every absolute number on the page, and every row instead records `host_temp_c_start` and `_end`, `host_throttle_count_start` and `_end`, and `host_throttled_ms` as the evidence.

**The host condition is a required statement of the page, in one plain sentence of its setup block** (PROTOCOL.md section 2, the host-condition bullet; DECISIONS #177): the host is thermally limited, every timed cell starts from the same temperature (the pre-cell temperature gate), and engines are compared within one pass, not across passes. The sentence states the condition and not the evidence: no temperature, throttle counter or throttled-time figure goes on the page (BUGS.md F71 still holds for those).

**The 7.3 TB disk is not the bench disk.** `/dev/sda` is rotational and mounted at `/mnt/hdd8tb` for backups. Everything measured lives on the NVMe. The split has to be explicit, or a reader would discount every I/O number.

The page's setup section is this block, read from `lscpu` and `lsblk`, not derived from a row. The payload's `hosts_recorded` list is not rendered. Every row records `bench_host`, which the runner refuses to leave unset at paper tier (DECISIONS #74).

## 1. Engine identity: commit, not version

ArcadeDB is pinned by **upstream commit SHA**, not by a release number. The build line reads `<release>.dev0` for every commit of a release line , so a version string cannot identify what ran, and printing one while claiming the page ships the upstream engine unmodified is a contradiction. A stable release pin reads its release number (`26.11.1`), and `engine_commit` is still the identity: the jar's own build number.

- Every row carries `engine_commit` (short SHA of the upstream commit the wheel and server image were both built from).
- The page prints it as the engine identity, linked to the commit on GitHub. Every ArcadeDB row is named from its own engine string and commit, never from an image tag; served rows carry the row's `server_image_ref` (BUGS.md F16, F32). The page header lists the identities actually present.
- Embedded and server arms in one table are built from the SAME commit, paired, and run the same JVM (DECISIONS #54).
- **Two builds, two arms (26.11.1).** ArcadeDB has two builds of one release: `arcadedb` (the native image, the default install) and `arcadedb-jvm` (JPype and a bundled JDK), both built from one engine commit. A page whose frozen rows hold the native build shows every in-process ArcadeDB arm twice, side by side, with the build last in the label: `ArcadeDB (embedded, native build)` and `ArcadeDB (embedded, JVM build)`, `ArcadeDB (embedded, fp32, native build)` and so on, in every table that has the arm (the lifecycle table puts the build after the situation: `Graph (embedded, native build)`). The native build comes first. The build is `engine_backend` on the row; a row without it, or with it empty, is the JVM build (`arm_identity.build_of`). The served ArcadeDB arm stays one arm: the server is the same Java server whichever package drives it, and its rows carry no build. A freeze of rows from before 26.11.1 has no native row, so it prints no build and renders as it always did. `BENCH_ENGINE_BACKEND=native|jvm` still freezes one build on purpose; the labels then still name it.
- **Both builds, one engine commit, or no page.** `export_web` refuses a freeze whose native and JVM rows name different `engine_version` or `engine_commit` values, and `page_check` fails the same page again (`_check_build_pair`). The gate also fails an in-process ArcadeDB arm that names no build on a page that names builds, two builds of one arm and size whose `version_name` differ, and a build that has a row at a size where the other has none. That last case is not left out: the exporter prints the missing build as a declared absence of kind `not measured` (a whole-row declaration with one generated sentence per table and build, naming the arms and sizes), which the roster and the pair gate read as accounted for. A table never takes a median over both builds: the exporter groups on the build and `_one_version` refuses an entry that spans two. Where the lifecycle table holds both builds its start column is `engine start ms`, the `start_jvm()` call on the JVM build and the library load with the isolate creation on the native build, and a sentence under the table says so. Not yet build-aware: the dense and sparse multipass overlays (files, not frozen rows) carry no build, so on a page that names builds the gate refuses their ArcadeDB embedded arms until the overlay says which build it measured.
- A campaign FREEZES one commit and holds it start to finish. Upstream landing a fix mid-run does not restart the campaign; it becomes a dated changelog entry and a candidate for the next re-pin.
- Re-pinning is a deliberate, dated act recorded in the changelog with what moved. No table falls back to an older pin, anywhere (DECISIONS #62).
- **One ArcadeDB version until the final DBBench release, then history (DECISIONS #189).** Until the final DBBench page and repo are released (after the late-November 2026 paper), a new ArcadeDB release's pass REPLACES the old one: after one scripted old-against-new comparison (a regression is filed before the next cut), the old version's ArcadeDB rows, page data, pin-specific code, pinned test fixtures and wording are removed. Comparator rows are kept across it and carry their own engine's version, never ArcadeDB's. From the final release on, a new engine version ADDS rows and the page keeps the history:
  - every table and chart shows one row per engine, its newest version, labelled with the version and the date measured; two versions of one engine never share a table;
  - a dated changelog (`/history`) has one entry per update with what moved, and links a frozen, static snapshot of the page as it stood before the update; the paper's state is the first snapshot and keeps a permanent URL;
  - a per-cell version history (the value per version) is added once an engine has two versions measured;
  - a history line connects only rows measured on the same host with the same instrument; a hardware or protocol change starts a new line, and the changelog says why.

Comparators are pinned by image digest and carry a version name, recorded per row from the image they ran on. A comparator row with `version_name: null` is not publishable. Embedded comparators name the engine core, not the SDK (BUGS.md F39).

## 2. Tables

**The page speaks the reader's language, not ours.** `export_web` strips citations to documents nobody outside this repository can open (`DECISIONS #82b`, `BUGS F55`, `FAIRNESS F1`) from every reader-facing string where the payload is written, and refuses what it cannot repair (`_refuse_internal_refs`). It also refuses our hostnames in prose and in dict keys. The same applies to our plumbing vocabulary, where no refusal is possible because some of it is stamped into rows that already exist: `lane` (say what the table measures), `cell` where it means a benchmark run, `the campaign` (say "the real run"), `arm`, `harness`, `frozen rows`, `this file`. Provenance stays exact: the generator's path, the source files, a container id, `bench_host` in the frozen CSV. The test: if a sentence would make a reader ask "what is a lane?" or "which machine is mini?", it is written for us and gets rewritten. The reasoning belongs on the page, the filing number does not.

**Where the table specs live.** The generated block "Published tables" at the end of this file lists the tables, rows, sizes and columns of the published payload; `refresh_web_page.py` rewrites it on every publish. The columns of a table are the exporter's per-table metric list and its rows are the arms in COMPARATORS.md; this file does not copy either. When the payload and this prose disagree the payload is right and this prose is corrected (DECISIONS #102). Every table needs an id, a title, a dataset line, explicit columns and rows, a source link to a tracked artifact, and conditions, which are generated or registered sentences only (section "What the page may say while a campaign runs"). Tables planned and not built: CAMPAIGN.md section 7, row 33. Retired and not coming back: `l3smp` (folded into `l3s` as warm columns), `l1` and `l1olap` (the synthetic document set is not run, DECISIONS #67 and #72), `l1tpc` (split into `docs_oltp` and `docs_olap`), `l3s_nocompact` (operator material, DECISIONS #71), `ops_build` and `ops_disk` (realised as the ingest pair and the disk column on every table).

`e4` and `pycost` are fed by bench-host artifacts, not by a lane the runner runs. `pycost` is OMITTED until its artifact is re-measured at the pin, because that artifact carries no engine version and `version_consistency_check` refuses a table of numbers that names nothing that produced them. An artifact-backed table is dated by its own `instrument` stamp where it has one, else by whether its path embeds the pin being published (BUGS F106); a fixed filename gets the conservative answer.

**A landing publishes one lane at a time, and the page says which tables are not measured yet.** `land_stage --only-lanes` scopes the pull, the freeze and the gates, and the scope is CUMULATIVE: the lane being landed plus every lane already on the page, read from the published payload through `export_web._TABLE_LANE`. Without that a landing rebuilt the page as though no other lane existed (BUGS F111). `refresh_web_page` compares the lane pages' `tableId` list (`src/lib/dbbench/lanes.ts`) against the payload and writes a `pending_tables` entry for each table absent, which the page renders in place of the table. A missing table that is NOT declared is a hard refusal (BUGS F95, F109), and so is a table the payload carries that the page's prose never renders.

**What every table carries.** The same measurement set (DECISIONS #89): one cold column per query-set (`cold_first_query_ms`) where the lane has one, warm latency per query at p50 with p99 on the headline query only, throughput where the operation has a rate, recall where the index is approximate, peak memory, and on-disk size after the workload. A table that omits one states why in its conditions, and `page_check` fails one that does not. An operation an engine cannot express is a declared absence (DECISIONS #88): the cell is a dash and the condition names the engine and the operation.

**A dash means that and only that (DECISIONS #111).** An engine that RAN and did not finish keeps its row and prints the outcome in the cell: `>2h` for the tier's cap (derived from `runner.TIMEOUT_BY_SCALE`, so `>15m` through `>48h`), `OOM` for an envelope failure (the kernel's kill at the cell's memory cap, or the engine's own out-of-memory error inside that cap, the same for every engine), `lost` for a dropped connection, `err` for a failure inside budget whose cause will not classify, `wd` for a withheld wrong answer, `re-run` for a cell measured before a fix to our own harness and being measured again. A vanished row reads as an untested engine, which flatters whichever engines finished. The legend is generated from the marks present and refuses one it cannot define. A harness failure never gets an engine mark, and a cell skipped because we expected it to be slow is published as its bound or not at all, never as a blank. The cap each cell runs under, and the censoring that follows from it at larger sizes, are the cap rule of PROTOCOL.md section 2 (DECISIONS #188); `export_web` applies it at report time to every row. The queue chain is CAMPAIGN.md section 6.

**`re-run` marks our own mistake, and clears itself (DECISIONS #117).** A cell or a row measured before a fix to this harness stays on the table with `re-run` where its number would be, plus a generated note saying what was wrong. A marked cell carries text rather than a median, so nothing that ranks or averages reads it as a measurement. `export_web.STALE_UNTIL_RERUN` (and `LIFECYCLE_STALE` for the lifecycle table, which folds by situation and size) lists each case as a table, an engine, a column (or none), and a test that recognises a row measured BEFORE the fix. It is keyed on row fields, never on a date: the re-measured rows supersede the old ones under the canonical-row rule and fail the test, so the numbers return at the landing that carries them with no list to edit. Each case names the BUGS entry for its fix, and a row it withdraws is kept out of the censored-cell notes, so our kill never prints as the engine's. `_rows_behind` reads a table whose lane has one workload (mapped to `None`) as any workload.

**Sizes (DECISIONS #108).** Each table carries TWO sizes wherever a second one is affordable and informative, because one point cannot tell a query that moved elevenfold from one that did not move. The large size is a ROW GROUP beside the small one, not a switch, and an engine with no row at it is a declared outcome under #103g (censored, envelope failure, or failed inside budget), never a reason to withhold every other engine's rows. Graph analytics is the single one-size exception, the full SF1 network, because the full network at SF10 is not feasible. No table accumulates two generations of ONE size and no new table is made for a size.

**Per-query budgets (DECISIONS #82b, #100, #100a, #106, #120).** Graph analytics, the graph table's four transactional reads (one budget per read spanning both passes), time series, and document analytics censor per query rather than per cell. The budget is per lane, per tier and per query, identical for every engine on its table, and read from `budgets.py` (derived from the bench host's frozen rows, #106); the lane constants (`graph_common.OLAP_BUDGET_S`, `graph_common.OLTP_READ_BUDGET_S`, `l4_tsbs.QUERY_BUDGET_S`, `l1_tpc.OLAP_BUDGET_S`) are only the fallback, and each row says which it used (`<q>_budget_source`). The page prints each budget from the row, never from prose. A censored analytics or time-series query keeps its cold pass and its answer digest; a censored read answered fewer starts than its neighbours, so its answer is declared (`censored: ...`) and not compared. Either way its p50 and p99 are over what it reached, and the table names it beside its counts note. No other lane has a per-query budget.

### Vector

Sizes: `l3s` three, 100k / 1M / 8.84M (the whole Big-ANN sparse track); `l3d` two, 1M and 10M (SIFT1M and DEEP-10M), both kept because the vector tables exist to show scaling.

- **`l3s` rows.** ArangoDB, MongoDB and SurrealDB have no row and are declared under the table (cannot express: none has a sparse index type, each with its own documentation cited, DECISIONS #95b), which is what the coverage table reads. The table has one ingest timer: every engine builds the index as it ingests except pgvector, whose index build follows its load and sits inside the same single timer. Cold and warm columns with their gain come from the sparse multipass driver (DECISIONS #89)
- **`l3d` rows.** The int8 arms of Milvus, Qdrant and sqlite-vec print at 9.99M only (`make_paper_tables.MP_ARMS_SMALL`). The table records `ingest s` and `index s` separately where the engine has the boundary, beside the single pair (#74). Warm columns come from the dense multipass driver.
- **Dense mutation.** Insert into a built index and delete from one, each followed by a search and its recall, run at the 1M tier only (#82d).
- **One protocol for both dense sizes.** `_dense_overlay_entries(scale)` reads `dense_mp5_<pin>` for 10M and `dense_mp5_small_<pin>` for 1M, and a partial directory refuses. No single-pass dense row is on the page; the single-pass campaign rows feed no page table.
- **`l3d_params`, when built,** makes the maxConnections-32-against-M-16 argument checkable and discloses that sqlite-vec is `exact_scan_no_ann`, brute force rather than an ANN index.
- **Dense build cache.** The fp32 arms are pinned to the corpus (`graphBuildCacheSize=9,990,000` at 9.99M on both deployments) and the INT8 arms run the engine default (DECISIONS #56; the percent knob is unread for inline quantization). The condition line must say: "ArcadeDB fp32 build cache pinned to the corpus size (9,990,000); INT8 at the engine default; comparators have no equivalent setting; see #7146 for the default's cost." At the default the served fp32 build sizes its cache to a fraction of the corpus and the embedded build to the whole of it, so the gap is the cache sizer and not the transport (DECISIONS #55, #56). The cache ablation is operator and upstream material, never a page table.

### Graph

Sizes: `l2` two, SF1 and SF10 of the persons-and-KNOWS projection, since per-seed reads never touch the message half. `l2olap` is the ONE table left at a single size, the full SF1 network (`sf1full`, `only_scales`), which LSQB's nine need and which SF10 cannot carry; an engine absent from a size is a declared outcome.

- **`l2`.** Seven operations: point lookup, one hop, two hops, three hops filtered on the far end, insert, update and delete. Every read runs against a fresh seed set per repetition and the three writes run 1,000 each per repetition, in both durability classes (#90). No cold/warm split: every operation runs against a built, warm database. Every engine traverses the same persons-and-KNOWS projection, each friendship stored as one KNOWS edge and every question asked undirected (CAMPAIGN.md section 7, row 56).
- **`l2olap`.** Fourteen query columns (DECISIONS #104), each asked of the whole graph and run 100 times per repetition under the graph lane's per-query budget. Five are hand-written (average friend age by city, friendships within a city, most friends, degree distribution, triangle count); two of them aggregate a property along the edges, which LSQB never does, so they stay. Nine are LSQB's pattern-matching counts, taken nearly verbatim from the published Cypher (undirected KNOWS, as LSQB writes it) and translated into AQL, MongoDB aggregation, SurrealQL and SQL/PGQ, with every digest agreeing on the slice across the graph engines and nothing declared unexpressible (#104a, #104b). The page's wording of each is the label map in `export_web`. The friends-of-friends pair (Q6 and Q9) is excluded at the full network (DECISIONS #109) and the table says so.
- **Reading `l2olap`.** A censored cell carries its cold-pass digest and is a result, not a hole (#104a); the triangle count is the cell most likely to exceed its budget, and a named censored cell with its budget stated is printed the way the embedded SurrealDB cells are (DECISIONS #82b). The degree histogram and the triangle count return a small deterministic answer, so they are the strongest equivalence checks on the page. The p99 is on the headline query only (average friend age). The cold column is the first query of the session, most friends, timed once on a freshly opened database. The view build is charged to the arm that builds it and printed as `view build s`, blank on rows without the view. The view-off arms are section 4b.

### Documents and time series

Sizes (#108): `docs_oltp` and `docs_olap` TPC-H SF1 + SF10, `l4` 100 + 1,000 hosts; `docs_oltp`'s SF10 is the first size to drop if the matrix does not fit.

- **Documents are TPC only** (DECISIONS #67): `docs_oltp` and `docs_olap`, split by `_restructure_tables` from one lane, with PostgreSQL beside the default arm. The tuned PostgreSQL arm (`postgres_tuned`) is an ablation of one image's defaults and stays off both document tables and the durability table, because it reads as a second engine (DECISIONS #76).
- **A table may lose its ArcadeDB row only by declaring it** in a condition a reader sees, naming ArcadeDB and giving the reason; `page_check` passes a declared withdrawal and fails a silent one (BUGS F42, F43: answer checking found ArcadeDB's two queries were not the questions the comparators answered, and both errors made its numbers faster than the truth).
- **Revenue queries count what they sum.** The revenue total and the revenue by month count the rows they aggregate and compare the count exactly (DECISIONS #94, upstream #7609 and #7611): the count is part of the answer and not a page column, and without it a lost row sits inside the sums' rounding at the largest tier.
- **`ingest s` and `index s` follow `ingest total s`** wherever the rows carry the index split (FAIRNESS F14); `ingest total s` keeps its name and its meaning, the whole of `build()`. A column no row fills is dropped. Every table with the split carries a generated sentence saying what the two phases are and that they do NOT sum to the total, because each adapter starts its ingest clock after its own setup (BUGS F101). `e2` records the split too (`bench_common.index_split`).
- **`docs_oltp`.** Six operations: TPC-C new-order and payment and the four single-record operations (insert, read, update, delete by key), 1,000 of each per repetition, with OLTP ops/s the rate of the two transactions together. The p99 is on new-order only, every write runs in both durability classes, and the rows declare no cold/warm split. The four single-record operations exist because nothing else on the page times the simplest thing anyone does to a database (DECISIONS #82a); each records its answer digest, so a create that wrote nothing fails the equivalence gate instead of printing a fast number.
- **`docs_olap`.** Five queries over the whole line-item table: TPC-H Q1 and Q6, the top ten parts by revenue, the count by ship mode, and revenue by month, 100 iterations each under the document analytics budget (#100a; censored cells are counted in a generated note). The cold column is Q1.
- **`l4`.** Six TSBS queries, 100 iterations per repetition under the time-series budget (#100): the newest reading per host (TSBS last-point, asked unbounded), the same bounded to the past hour (measured and kept on the row, not printed), the twelve-hour aggregate, per-host hourly (a double group-by), the high-usage filter, and the grouped, ordered, limited query. The cold column is the newest reading. ArangoDB and SurrealDB run it on a plain table with a composite (host, ts) index, SQLite's footing (#100). The ingest split reaches `l4` when its rows carry it.
- **An index defined before the load (humemai/arcadedb-embedded-python#396).** A table with an `index s` column names, in one generated sentence, the arms that define their index before the first row, so their small `index s` does not read as a free index: the arms whose rows carry `index_before_load`, and the arms in `export_web._INDEX_BEFORE_LOAD_REPORTED`, whose adapters do not set the flag (ArcadeDB's document time-series arms, ArangoDB's time-series arm, SurrealDB's embedded cross-model arm). The rule is the same for every engine; an arm that also builds a larger index after the load prints a real `index s` and is not listed.
- **1,000 hosts is near the envelope.** The time-series lane parses the line protocol in Python inside every cell, about 29 minutes of that tier before any engine work, so the size is priced as parse plus engine. The ArcadeDB document path held 24.4 GiB of its 32 GiB cap there; any proposal for a larger tier starts from that, because an engine at three quarters of its allowance at one size is an ENVELOPE failure at the next (#103g), which is evidence for nothing about latency.
- Every document table publishes ingest rate beside OLTP ops/s: publishing the win without the loss is selective.

### Cross-model, deployment, embedded

Sizes: `e2` and `e2atom` two, 50k and 500k products (the larger so retrieval recall is measured on more than a toy, #103), the larger a second row group rather than a replacement (#108); `e4` keeps its six result sizes, `pycost` its two workloads.

- **`e2`.** Four operations (#82c): the composed transaction (a vector hit, a one-hop expansion and an update of the touched products, 300 per repetition, both durability classes), the same transaction interrupted (`e2atom`, which kills the process between the writes and reopens), a retrieval path, and a graph-filtered vector search. The two read paths carry recall measured against a brute-force answer over the same filtered candidate set, because an engine that filters after the search shows it there and not in latency. `e2atom` is the page's central claim, all-or-nothing across three models against a composed stack that cannot promise it; the trial count and the torn count are pinned by `page_check` against the artifact, and what they say is written at the freeze (#102).
- **What the transaction holds is declared per engine, not equalised (DECISIONS #118).** The update is atomic; the two reads that choose the products may run outside the transaction, because that is what every engine on the table can do. Each adapter declares a `TXN_SCOPE`: `whole` (reads inside the transaction with the update), `update` (reads first, only the update in a transaction; MongoDB's is asked of its server at build time and recorded as `txn_scope`, since mongod refuses `$vectorSearch` inside a multi-document transaction, #98), or `none` (the composed stack, whose two systems share no transaction; the Qdrant server runs beside Neo4j in one container, #117). A generated sentence names the engines on each side (`export_web._txn_scope_note`). ArcadeDB keeps its reads inside, the setting that does not flatter it. DuckDB runs VSS and DuckPGQ in one engine (DECISIONS #131 item 4).
- **`e4`** runs as a runner lane (`e4_decomp.py`). Since CAMPAIGN.md section 7, row 72 it measures every HTTP arm under two Python clients (the probe's own, a urllib shim that opens a connection per call, and lean_http's persistent connection) and names the client in each HTTP column; `export_web._e4_arms` refuses a pin directory whose repetitions disagree about the clients, and an artifact measured before the axis keeps its three columns and names no client. It carries no derived deployment-cost columns, CPU time, crashes or scratch write (DECISIONS #73).
- **`pycost`** prints time in ms (p50, column 7 of `mini_results.csv`; column 6 is the mean and is never printed) and vs Java.

### Operating it

- **`lifecycle`** is both a page table and a regression gate (section 4). It compares the embeddable multi-model engines: the single-model embedded engines are not on it (DECISIONS #139, amending #131 item 5), and their arms stay built and off the roster (COMPARATORS.md, "Not added, and why"). Seven situations (empty database, documents, documents with ten indexes, graph, sparse vectors, dense vectors, time series), each ArcadeDB embedded and server. SurrealDB embedded runs the six it can express, with sparse vectors and the analytical view declared with the parse error (#95b); graph with the analytical view is withheld for ArcadeDB (rule 7). Sizes: 10k, 100k, 1M and 10M for documents, time series and dense vectors. There is no cold/warm split (it is itself the cold measurement) and no throughput or recall, and the conditions say so rather than leaving columns blank (DECISIONS #89). Server rows are labelled `<situation> (server)`, run `open database` / action / `close database` over HTTP, and have null JVM-start, first-open and cold-process columns because a server is already a process. SurrealDB rows carry no JVM start either, since its core is a compiled extension the import loads; the other embedded comparators' rows are named in one generated sentence saying the same, and LadybugDB's primary-key index, Chroma's and LanceDB's open, LanceDB's missing close and sqlite-vec's exact scan each get a sentence when that engine is on the table (the exporter's lifecycle prose). A situation an engine cannot build prints as one sentence per engine with the head of its adapter's reason. Embedded rows print no disk, because the database sits on a host bind mount the disk reading cannot see; those cells are blank with a condition (DECISIONS #71).
- **`durability`** has no lane of its own: one row per engine and operation, from the write cells of `docs_oltp`, `l2` and `e2` run in both classes (#90), the Size column naming the operation. Engines with no setting to relax (DuckDB and its DuckPGQ arm, LadybugDB, Neo4j and the arms built on it) print one number in the waiting column and say so; the SurrealDB server runs both classes (`sync=never` and `sync=every`, read back, BUGS F165). The read row is the control. The ratio is what waiting costs that engine on that operation and is not a claim about any other write.
- **`restart`** covers every served engine on the page, each on ONE model's data loaded by that model's own table (DECISIONS #139 item 2): documents at TPC-H SF1 and SF10, graph at LDBC SF1 and SF10, dense vectors at 1M, time series at the two TSBS sizes. ArcadeDB's server runs all four, so every group has it, and a tier of comparators alone is withheld. PostgreSQL stands for pgvector, PG+AGE and TimescaleDB (one server binary). The scale names the model, and rows compare only within a size.
- **`multimodel`** covers the five multi-model engines, every arm of one engine folded into one row: ArcadeDB, ArangoDB, MongoDB, SurrealDB and PostgreSQL + AGE (DECISIONS #131 item 9; its graph and cross-model arms, both on the `dbbench:pg-age` image, fold through `export_web.MULTIMODEL_ALIASES`). It is derived by the exporter from the other tables and re-derived by `page_check` at every publish (#95a); the roster of five is the one typed thing. One column per table on the page, each cell measured, declared (with the reason under that table) or no arm. It carries no number.

**The lifecycle scenarios.** A database is built, read, written to and reopened after someone else wrote; those states cost different amounts and the difference is the finding, so each is its own column.

| scenario | what it asks |
|---|---|
| `build` | create, load, create the index/view, close. The session that OWNS the build, and where a close-time rebuild doubles it (#6489). |
| `clean` | reopen, touch nothing, close. |
| `read` | reopen, run one query, close. |
| `write` | reopen, commit one row into a scratch type, close. Held CONSTANT across situations; measured, not on the page (DECISIONS #73). |
| `write_own` | reopen, commit into the situation's OWN structure, close. The constant write leaves a vector index clean; only this dirties it. |
| `write_own_read` | write then read in one session. Neither half alone shows the cost (#6641). |
| `stale` / `stale_read` | reopen a database a PREVIOUS session wrote to, so a persisted derived structure is invalid on arrival. |
| `drop` | reopen, drop the accelerator, close. Single cycle, never a median: the second cycle would find nothing to drop and average in a no-op. |

**Time the actions, not just the ends.** Every scenario reports `open + action + close = session`, and the page quotes the session: timing `open` and `close` alone misses where a query-triggered rebuild lands. The lane's page columns are the cold-start decomposition (4 columns), then per scenario: open ms, action ms, close ms, session ms.

**Cold start is four numbers, not one.** Measured in a fresh subprocess per situation: `import_ms` (interpreter and module import), `jvm_start_ms` (`start_jvm()` alone), `first_open_ms` (first `open_database()`, JVM already up) and `cold_process_ms` (what a CLI actually waits for). A page that quotes a warm open without the cold process beside it is off by orders of magnitude for anything CLI-shaped, and embedded use is mostly CLI-shaped. On the native `arcadedb` build there is no JVM: `jvm_start_ms` is null and `engine_load_ms` (the engine library load and isolate creation; `start_jvm()` on the JVM build) is the same step, so compare `import_ms + engine_load_ms` across the two builds. Two columns come from a second fresh process: `cold_first_query_ms` (the situation's first read after the first open) and `cold_query_process_ms` (process start through the end of that read). The definitions are in the docstring of `l5_lifecycle.py`.

### Rendering rules, every table

- **One row order, one column pass.** `export_web._finish_table()` runs last over every table: tier, ArcadeDB first, then comparators alphabetically; embedded before server; int8 before fp32; stable inside a group. Every metric a row carries becomes a column. A builder owns its numbers, not its layout (BUGS.md F25).
- **Column set and ingest names.** A lane's columns are the exporter's per-table metric list: one warm median per query, a ninety-ninth percentile for the table's headline query only (the first in the list), one cold column for the first query after the database opens where the lane has one (a transactional cell declares in `cold_warm_na` that it does not), throughput where the operation has a rate, recall where the index is approximate, peak memory, disk, and on the dense table ingest and index build as separate timers. Ingest rates name the type: `ingest documents/s` (documents, TPC), `ingest vertices+edges/s` (graph), `ingest points/s` (time series), `ingest+index vectors/s` (both vector tables), `ingest+index vertices+edges/s` (the cross-model set, whose load includes the vector index). The word "records" does not appear as a column name.
- **Ingest is a column pair, not a table.** Every table whose rows loaded something shows `ingest <unit>/s` and `ingest total s`; on the vector and cross-model tables the timer includes the index build and the note says so. The sparse table states that no engine on it has a boundary. Derived rates use `_rate(count_fields, seconds_field)`, aggregated per row like any field.
- **Latency columns.** p50 on every query; p99 on the headline query of each table (DECISIONS #89 as amended); analytical queries run 100 iterations per query per repetition and record `*_p50_ms` and `*_p99_ms` on the row whether or not the page prints both. p95 is not shown anywhere. No per-table aggregate is published.
- **No sentence on the page cites a document the reader cannot open.** `export_web` strips such citations at the single point the payload is written, rather than at the many places sentences are built, and what the stripper cannot repair it REFUSES to publish, because a sanitiser that silently misses a form is worse than none. Fields that name an artifact on purpose are provenance and stay exact: the generator's own path, a table's source files.
- **The durability condition is generated, not typed.** Each table's note comes from the engines that table shows (`export_web._durability_note`): the matched relaxed class, then any engine that waits for the disk at every commit, then any engine whose behaviour at commit could not be established (FAIRNESS.md F10, DECISIONS #81).
- **Peak memory and disk on the multipass-fed tables come from the campaign cell of the same arm** (same build, same envelope); the served arm's multipass file sees only the client container.
- **The memory column is owned memory (issue #353).** Every `peak memory GiB` cell is the row's `peak_owned_mib_sum`, the anonymous peak plus the shared-memory peak, summed over every container of the cell, in GiB (`export_web.MEM_PEAK_FIELD`, `_peak_mem`). It falls back to `peak_anon_mib_sum` only for a row that lacks the field. The kernel's file cache stays out for every engine alike. Because shared memory is inside the cell, a PostgreSQL-family engine's cell is comparable with the others and the page carries no shared-memory disclosure; the plain PostgreSQL arm's cell is split into our Python client and the database by a generated sentence (`export_web._pg_memory_note`). `end_anon_mib_sum`, and the server's anonymous peak that `export_web._server_hit_envelope` reads to recognise a killed cell, are not this column and stay anonymous.
- **Disk on every table.** A blank disk cell is a row measured before the instrument, an engine with no disk at all (a spec's `in_memory` list), or a served row with no server reading (BUGS.md F38); the note under the table says which. A served row's disk is the server container's growth alone, the client is only the driver. Neo4j's value includes its preallocated 256 MiB log files and the note says so (BUGS.md F27). Units are GiB (BUGS.md F40). When the reading is taken is section 4a.
- **A cell with no row is accounted for by outcome, and the outcomes are not the same thing.** `export_web._censored_notes` reads every failed cell out of `runs.jsonl` and writes one sentence per cell naming the engine and the size. A cell that ran past the tier's cap is CENSORED and the note names the cap. A cell that failed inside its budget for another reason carries what it reported, so a lost connection does not read as slowness. A cell the kernel killed at the tier's memory envelope (`rc=137` with `oom_killed`; for a served cell `server_oom_killed`, or on an older row a failed cell whose server's anonymous memory reached 99% of its cap, `export_web._server_hit_envelope`) is an ENVELOPE failure: the engine did not fit the cap every engine on that tier was given. So is a cell where the engine stopped itself with its own out-of-memory error inside that cap (DuckDB's `OutOfMemoryException`, a JVM's `java.lang.OutOfMemoryError`, PostgreSQL's SQLSTATE 53200): it prints `OOM` the same way, for every engine. `export_web.ENGINE_OOM_SIGNATURES` lists the texts it recognises, each with where it was read, and `export_web._row_engine_oom` looks for them in the row's `error` and in its client log. An envelope failure is not evidence for a latency claim in either direction, and the page must not let it read as one.
- **Rendering.** Integers print as integers (0, not 0.00; 40, not 40.0); values below 0.1 print with two significant digits; a missing value is a dash. Every table carries a Size column and direction arrows, and the best value per column within a size is bold.
- **Vocabulary.** Documents, not tables; one word per concept (Python package, embedded/server, comparator, size, cold/warm, trial). The page never says tabular or relational.
- **Both deployments wherever the engine has a served form** (DECISIONS #61): ArcadeDB runs embedded and server on every table, and a comparator that offers both runs both (SurrealDB). Quantization: fp32 and int8 only; fp16 is not run.
- **Absences are declared, never blank** (DECISIONS #92, #95b). An engine is left off a table only when its documentation and an exact error show the query cannot be expressed, and then the sentence under the table says so with the citation; a censored or withheld cell is named with its reason. The coverage table reads those declarations.
- **Before calling a page complete**, scan the exported JSON per column for blank cells and per row for a missing version (BUGS.md F26 has the one-liner). The freeze counts rows; the reader sees cells.

## 4. Close cost is a bug, not a table column

Close and open cost get a page table AND an invariant, because a slow close is a defect class (DECISIONS #50) and this engine has produced several (#5747, #6489, #5872, #6067, #6722, #7183).

**The invariant (DECISIONS #50):**

> Close should be **O(what was written), not O(what is stored)**, and on the order of **100 ms**.

Grounded twice: close should not cost more than getting started, and it should sit under the ~100 ms at which a script stops feeling instant.

**"Getting started" is two numbers, not one.** A Java process reaches its first engine call in ~219 ms (`RuntimeMXBean.getUptime()`); a Python process takes longer (import, `start_jvm()`, first `open_database()`). No JVM figure may be quoted without its host, and the page uses the bench host's column. The page's story is embedded PYTHON, so the Python row is the one its close budget answers to.

**Quote JVM startup next to every session number.** At these magnitudes it is the larger figure: a 5 ms `open()` inside a process that took 219 ms to reach its first database call is not a 5 ms cost to anyone launching a CLI, and printing the `open()` alone flatters every embedded number on the page.

`lifecycle` runs as a gate, not just a report. It FAILS when:
- a situation's close time grows with row count while nothing was written (that is the O(stored) shape and it is always a bug), or
- any clean close exceeds 100 ms at any tested size.

Situations that pass (documents, all four index types, geo, sparse, time series) are stated positively: the multi-model substrate closes cheaply. The vector index is the situation that does not, and the table's condition says what is known at the pinned engine build: a no-op close grows with the index, and a session that writes and then searches pays a full asynchronous graph rebuild that `close()` waits on (#7183, fixed upstream in #7191).

The Graph Analytical View is not rebuilt on every open (#6583 via #6588, #6632 via #6633), and an invalidating commit does not stall the next query (#6641 via #6642). The page must not say the view's speedup is paid with a per-session scan; it is not. What the view still costs per session is in section 4b.


Cold open is measurable: `pagecache.evict()` drops a database's files with `posix_fadvise(DONTNEED)` and verifies with `mincore` that they left. No root, and it evicts only the named files, so the rest of the host stays warm and the number means "this database is cold" rather than "the machine is cold".

## 4a. When on-disk size is measured

On-disk size is not fixed at the moment a database closes, and a number that depends on when we looked is the same class of defect as the memory column. It drifts three ways: delayed block allocation (down-counts what is still dirty), background compaction retiring obsolete segments (drifts DOWN, sometimes minutes later), and WAL truncation after checkpoint.

**What the page prints today.** `disk GiB` is a column on every table that has it (DECISIONS #61), not the separate table once planned. `disk_data_mb` = the engine's writable layer plus its volumes after the cell, minus the same engine's empty footprint; for a served row, the server container alone. It is a POST-RUN reading, taken after the queries, and every table that prints it says so in its conditions. `container_disk()` syncs first, samples until two consecutive readings agree within 1%, measures the writable layer AND the volumes (PostgreSQL reported `SizeRw` unchanged from empty while 1,017.5 MiB sat in its volume), reads volume destinations from the daemon rather than a guessed path table, and returns `settled=False` with both readings rather than a bare number. The embedded arm takes one sample (`tries=1`) against a stopped container: defensible, since a dead process cannot compact, and stated on the row rather than left looking like a settled reading.

**The build-point protocol is not adopted; CAMPAIGN.md section 7, item 19 carries it.** The disk-settle rule itself is in PROTOCOL.md section 2. In short, the stricter reading measures at the point the build timer stops, right after the engine's own settle step (1); a post-query reading is a second column, never the headline (2); `settled=False` blocks publication (3); and the settle budget must exceed a compaction cycle (4). Land it deliberately, before a campaign, never between reps of a running one: giving the dense lane an ArcadeDB settle step via `idx.compact()` is a SILENT NO-OP, because `LSMVectorIndex.compact()` returns false unless a compaction was already scheduled.

## 4b. GAV is measured with the view ON and OFF, everywhere

The Graph Analytical View is an ArcadeDB-only accelerator, so an unablated number is a claim about a configuration rather than about the engine. Every graph OLAP cell runs BOTH arms:

    {embedded, server} x {the full SF1 network} x {BENCH_GAV=1, BENCH_GAV=0}   = 4 cells

All four cells are on `l2olap`. The view's build cost is charged to the arm that builds it and published as a column (`view build s`, absent on rows without the view).

Labelling: `l2_graph.main()` stamps `out["gav"]` as a real boolean and sets `backend_arm="nogav"` for the off arm. `BENCH_GAV` is in the runner's env allowlist; it was once missing, which would have built the view anyway and written rows labelled as the ablation, rc=0, indistinguishable from a real one (rule 5).

**The ablation must use the lane's real query set, not a stand-in.** On a small synthetic graph an openCypher two-hop count is SLOWER with the view than without. The published speedup (the pinned top-degree ratio, which is one query's number; the benefit varies by query and grows with the graph) comes from the lane's property-aggregation queries over neighbourhoods, a different access pattern. The view's benefit is query-shape dependent, and a probe that substitutes a convenient query measures nothing about the view the page publishes.

What belongs beside the pinned ratio: the view's cost per session is real. Its build is charged once (the `view build s` column), and a session that never queries the view pays a small cost at open since #6633 (section 4). The pinned ratio is a within-session property.

## 6. Gates

`refresh_web_page.py`'s invariant: *every page table and figure is generated from frozen rows, listed in the page manifest, pinned by `page_check`, and carries a source link to a tracked artifact.* `page_check.PROSE` pins every typed number in the page prose, including page-only tables through `lambda P:` references over the exported JSON; a reworded sentence fails ABSENT. `page_check` also fails if any table loses its ArcadeDB row against the published payload. `land_stage.py` is the publish-after-a-stage procedure: merge, regenerate, gates, then the diff, and with `--apply` the build, the commit in both repositories, and the push. PUBLISHING.md holds both. After a re-pin, the SERVED page is grepped for the previous pin's strings in every field, not just the labels (BUGS.md F16).

**The gates.** `refresh_web_page.GATES` is `equivalence_check`, `resource_check`, `provenance_check`, `fairness_check`, `page_check`, `version_consistency_check`, `version_pin_check`. `version_pin_check` is the only one that reads no rows: the others ask whether the measurements are sound, and it asks whether the files a human edits can still disagree about which artifact was measured -- every image digest and package pin across `runner.py`, `build_images.sh`, and the three Dockerfiles (`Dockerfile.pgage`, `Dockerfile.mongosearch`, and `Dockerfile.composed`), with COMPARATORS.md stating them for a reader (it prints how many of each it compared); BUGS F76 is what it exists for. Its `--runtime` mode is not a publish gate: it runs the built images and reads their versions back out, as a STAGE PREFLIGHT rather than at freeze, because a check that can only run after the run is an autopsy (BUGS F90). `version_consistency_check` refuses a page where one engine wears two version strings or a comparator wears an ArcadeDB release number (BUGS F63). `resource_check` refuses a disk or memory value that cannot be right. The memory it reads is the page's column, owned memory, so an engine that keeps its data in shared memory needs no excuse there.

| gate | fails when |
|---|---|
| mixed corpus | rows in one table disagree on `n_docs` while sharing a `scale_label` |
| sweep tier | a published cell carries `tier != paper` |
| unexplained column | a rendered column is named by no condition and no methodology entry |
| false protocol sentence | a page sentence asserts an n that any cell it covers does not meet |
| unpinned literal | a numeric literal appears in page prose outside a pinned entry or a generated cell |
| labels | a corpus name, size, or dimension on the page disagrees with the artifact constant |
| close cost | a clean close exceeds 100 ms, or grows with rows while nothing was written |
| mixed instrument | one table holds rows measured under two instruments |
| durability class | a table's engines committed under different rules, or a row carries no `durability` |
| disagreeing answers | two engines of one table answer the same query differently at one scale, or an engine skipped an operation without declaring it unexpressible |
| one engine, two versions | a comparator wears two version strings across the page's tables, or an ArcadeDB release number appears on a comparator's row. Declared splits name two genuinely different artifacts and carry their reason |
| missing measurement | a table omits one of the standard measurements and states no reason |
| off-page name | a page sentence names an arm the page does not print (`OFF_PAGE_ARMS`) |
| undisclosed zero ages | a graph table is built from LDBC rows without the fixed age parse and does not carry the sentence saying their ages loaded as zero (BUGS F146, DECISIONS #119) |
| missing LDBC wording | a table built from LDBC data (`export_web.LDBC_DERIVED_TABLES`, or a dataset or size label that names LDBC) does not open with the sentence "These are not LDBC Benchmark Results." and a sentence that starts "How this differs from the LDBC standard:" (`page_check._check_ldbc_notice`) |
| undisclosed override | a table shows an arm that runs a PROTOCOL.md section 7 override (`override_registry.py`) and prints no sentence saying so, or a row of such an arm lacks the engine's own read-back of the setting or carries another value (`fairness_check` F15; CAMPAIGN.md section 7, item 21) |

## What the page may say while a campaign runs (DECISIONS #102)

Three kinds of text exist on the page, and only two are allowed before the freeze.

- **Generated**: cells, counts, budgets, censored and withheld cells, declared absences, the durability setting each row ran, the disk definition. Derived from the frozen rows or from constants imported from the code that ran, by a registered generator. Cannot go stale.
- **Instrument prose**: what a table measures, what its columns are, how to read them, the fairness setup, the licence table. Typed, carries no number that is not pinned, and describes the protocol rather than the outcome. Lives in the lane pages (`src/lib/dbbench/lanes.ts`) for the page body and in the exporter's prose registry for the sentences under a table.
- **Interpretation**: which engine moves between passes, which benefit is uneven, how far the comparators sit from one another, what the ratios say. Not written while the campaign runs. Written once at the freeze, when every row is in, each sentence with a pin, so a later re-measure that changes the number fails the publish.

A condition sentence on the payload that is neither generated nor registered fails `page_check`.

## 7. Methodology the page must carry

Once, at the end, linked from every table: the global conditions; the environment table (`cpuset`, `mem_cap`, `server_mem_cap`, `mem_split`, `heap`, `server_heap`); the machine block from 0a, stating that the cpuset is 12 threads on 6 physical cores, that the governor is `powersave` with turbo off (`no_turbo` = 1, the P-cores at 2.5 GHz at most) so frequency is not pinned, that the power mode is left as it ships, and the host-condition sentence of 0a (the host is thermally limited, so engines are compared within one pass, not across passes); the package DOES throttle under sustained load and every row records its temperature and the kernel's throttle counters (BUGS.md F45), but that evidence is INTERNAL and is not published in any phrasing (BUGS.md F71; the host-condition sentence states the condition, not this evidence) -- it is recorded so a question about the host can be answered off the page, and the serial-execution rule above is what the page relies on instead, and that the bench disk is NVMe while the same machine holds a rotational disk used only for backups; the overrides table from `PROTOCOL.md` section 7 with a column saying **which way each override moves the number**; the durability note (DECISIONS #70, #81, #90); engine identity per section 1; the query set by table (two operations excluded at the full graph network, #109), and which of them come from a published benchmark (those of DECISIONS #82d and LSQB's nine, #104); repetition counts per table (generated, not typed); how equivalence is checked, that every timed query's answer is digested and compared across the engines of its table, and which operations an engine declared it cannot express (DECISIONS #88); ground truth (how recall@10 is computed and against which truth); outcome accounting; a dated changelog; and "Reproducing this", linking PROTOCOL, FAIRNESS, CAMPAIGN, READING-RESULTS, PUBLISHING, and the frozen artifacts.

Beside every peak-memory column with a JVM engine on it, not only the ones that compare ArcadeDB variants: an arm that pins `-Xms=-Xmx` commits the heap, so its column measures reservation, not demand. The ArcadeDB arms, embedded and served, leave `-Xms` unset, so their column measures demand up to `-Xmx`, and the sentence names only the arms whose rows record a pinned heap. The sentence is generated (`export_web._jvm_memory_note`) from the rows. This never clears; it is stated, not fixed.

**LDBC wording (fair use).** [LDBC's fair-use policy](https://ldbcouncil.org/benchmarks/fair-use-policies) lets only a result audited by an LDBC-approved auditor be called an LDBC Benchmark Result; unaudited or derived work must say it is not one, credit LDBC under CC BY 4.0, and say how it differs from the standard. Every table built from LDBC data (`l2` graph OLTP, `l2olap` graph OLAP, and `restart` for its graph rows) therefore opens with `export_web.LDBC_NOTICE` ("These are not LDBC Benchmark Results", the credit, no audit, no endorsement) and its own deviations sentence (`OCT_PROSE[table]["ldbc_deviations"]`: which data and scale factors, which queries are ours and which are LSQB's, no LDBC driver or ACID/recovery test or price/performance, our own harness, embedded and containerised engines). Both are registered sentences, not prose typed per page, and `page_check._check_ldbc_notice` fails a publish when a table lacks either. A new table that reads LDBC data is added to `LDBC_DERIVED_TABLES` in the same change. No number from these tables may be called an LDBC result, or compared with an audited LDBC result, anywhere (page, paper, issue, post).

And a closing list of what the page does NOT measure: concurrency and load (it needs a non-Python load generator; our own harness is censored above ~4 clients by GIL queueing, and a bad concurrency table is worse than a disclosed absence); import, export, and backup; replication beyond the failover trial; strict durability for bulk ingest and reads (the timed writes run at both classes and the durability table prints them, DECISIONS #90); updates against a live vector index, where the dense table times an insert and a delete into a built index at the 1M tier and nothing above it (DECISIONS #82d); dense dimensionality above 128; anything across a real network; k other than 10.
