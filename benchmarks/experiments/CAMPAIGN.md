# Running a campaign

## The routine, end to end

Two loops, one inside the other. This is the whole procedure in order; each step names where its detail lives, and nothing below contradicts it.

Per campaign, once:

1. Settle the instrument before any cell runs: the query set, the measurement set, the durability rule, the fairness invariants, and the answer checking. A change mid-campaign splits the rows, so this is the only free moment (DECISIONS #82d, #88, #89, #90; PROTOCOL.md). The method pages in the package documentation (`bindings/python/docs/benchmarks/`) describe the same instrument without numbers, so they change in this step too, never later.
2. Smoke every adapter, one cell per engine per lane, and keep the evidence (the smoke's rows and logs). Smoke wherever a machine is free: nothing in the fairness contract touches a smoke, and the bench host is reserved only while a published cell runs, so a smoke on the real corpora there is both faster and a better test than a capped slice on the laptop. One runner per host, always: `runner.py` sweeps every `dbbench=1` container on the machine at startup, so it takes a host-wide lock first (`$TMPDIR/dbbench-runner.lock`, whichever checkout it runs from) and a second runner is refused at startup (BUGS F58).
3. Pin ArcadeDB: sync upstream to the release the campaign runs and build the wheel by the routine in `bindings/python/docs/development/upstream-bindings-pr.md`, run our Java reproductions on the built engine to confirm every fix it should carry is intact, and record the engine commit inside that wheel as the campaign's pin (the pin is the commit, not the version string, DECISIONS #49). For a stable release the pin is the release's own jar commit (26.10.1: `d36b4ca3a`), the wheel is the official jars plus this tree's bridge and package, and the pair is placed by the recipe in `.notes/bench/repin-round5/REPIN-START.md`. The served arm's matched pair is built from the same image by `build_matched_pair.sh` (HANDOFF.md). One wheel, one pin, held start to finish.
4. Re-pin every comparator to its latest stable release, smoking the risky jumps on their own (COMPARATORS.md, DECISIONS #87).
5. Run the campaign, landing each stage into the freeze (section 6 below).
6. Regenerate the query budgets from the campaign's own rows (`python3 derive_budgets.py > budgets.py` reads the freeze, `results/runs_paper.csv`) so the next campaign's caps are measurements at the corpora it will run rather than projections, and commit the table with the freeze (DECISIONS #106).
7. Freeze and run every gate including the manifest coverage check. Only now is interpretation written, which engine moves between passes, which benefit is uneven, what a ratio says: once, from the frozen rows, each sentence with a pin, so a later re-measure that changes the number fails the publish instead of leaving a sentence that used to be true.
8. Publish: `refresh_web_page.py` renders the freeze's 2026-11 rows onto the DBBench page (PUBLISHING.md), then `publish_results_asset.py` bundles the freeze and the payload as a release asset. A first campaign of a new instrument also follows PUBLISHING.md, "Moving to the next instrument".
9. Prune what the campaign made obsolete: superseded decisions, bugs that retired with it, retired markers, any withheld cell whose upstream issue has closed, and the typed sentences of an instrument no page renders any more, which are deleted from the exporter rather than kept.
10. Re-read every document the pruning touched, then rebuild both sites, the DBBench page and the package documentation, and check the links between them resolve in both directions (`uv run mkdocs build --strict -f bindings/python/mkdocs.yml` from the repository root).

Per stage, repeated inside step 5:

1. Write the queue script, lint it with `queue_lint.py`, and chain it behind the previous one (section 5 below).
2. Let it run. The session watches STATUS.txt and docker; investigate any failure before recording it, because a recorded failure is a published claim.
3. Land it with `land_stage.py`: pull the rows, exclude the backends still running, merge, run the gates, read the table diff, then apply, which commits the data and publishes the page. Use `--only-lanes` to land one lane while the rest of the chain runs; the scope is cumulative, so it covers that lane **and every lane already on the page**, and the tables of lanes never landed render as pending rather than vanishing (PAGE-SPEC, BUGS F111, F109). **Rehearse the landing before the stage that feeds it finishes** -- `--only-lanes <lane>` against the rows already in the store, without `--apply`. A rehearsal finds the defects that would otherwise fire at the moment the data arrives: a figure that died on an empty lane, a refused run that left its payload in the tree, a table publishing one median across two corpus sizes, and a landing that would have deleted the previously published tables. `--exclude-backends` matches by prefix, so a family name catches its served twin (`surrealdb_dense` also drops `surrealdb_dense_server`); when the next stage re-runs one arm of a family, exclude by time instead, `--exclude-since` set to the finished stage's ALL-DONE timestamp, and read the `dropped` line the script prints before applying. The script refuses LANDED unless the bindings commit moved HEAD and the push reached origin (a pre-commit hook that rewrites a staged file aborts the commit; the script retries once).
4. Regenerate anything derived from the rows that changed, such as the bottleneck memo. Do not write interpretation of the new rows on the page; that waits for the freeze (step 7 above).


How a full re-measure is executed on mini. `PROTOCOL.md` holds the rules a row must satisfy; this file holds the procedure that produces the rows. If the two disagree, PROTOCOL wins and this file is wrong.

## 1. The shape: parallel where nothing is measured, serial where it is

**Phase A, parallel.** Image builds, corpus generation and conversion, ground-truth computation, checksums, dataset staging. None of it produces a published number, none of it is timed, and it is the only place concurrency is free. Run it as wide as the box allows.

**Phase B, serial.** The measured cell, whole and undivided: build, settle, query, close. One at a time, full cpuset `0-11`, nothing else on the machine. This is `PROTOCOL.md` section 2.

### Why Phase B is not parallel

Phase B stays serial: memory binds before CPU (the tiers where the time goes admit a concurrency of exactly 1, and `runner.py` refuses more), and a neighbour cell evicts the shared page cache, shares the L3 and lowers the turbo clock, which moves the rows of a lazy-loading engine like ArcadeDB and not the comparators', unevenly.
The prize is small (perfect intra-lane parallelism saves 10-16% of a pass) and the better levers are free: parallelise Phase A, and lower a tier's N only as a disclosed, reversible reduction (PROTOCOL).

### Why the build/query phase split is not adopted

The split (build every cell in parallel, stop the engine, reopen it for a serial query pass) is not licensed: every number behind it is N=1, and no tier whose working set exceeds the page cache has been measured, where a reopened pass would favour the lazy engine and not the comparators, silently, in the direction that flatters us.
It also needs an engine whose dense close is not a second graph build (upstream #6490, #6489); `l3d_dense.py` records the mechanism beside its `BENCH_SKIP_CLOSE` switch.

## 2. Staging: smoke, then the chain

A campaign does not advance past a step until the one before it is green. A defect found in the chain costs a stage.

1. **Smoke.** One cell per engine per lane, N=1, cheapest tier. Proves the images, the corpora, the adapters and the recorded schema. Rows go to a scratch results file, not to `runs.jsonl`.
2. **The chain.** The published tiers on the bench host, stage by stage (section 6), each landed with `land_stage.py` through the same gates.

A stage that produces rows no gate admits has failed even if every cell exited 0.

## 3. What every cell records

Beyond the lane's own metrics:

- **Memory.** `peak_anon_mib_sum`, `peak_shmem_mib_sum`, `peak_owned_mib_sum` (anon + shmem), summed across every container in the cell. Anon alone misses a POSIX-shmem buffer pool entirely, which is why the page's memory column is `peak_owned_mib_sum` (issue #353).
- **Disk.** `SizeRw` plus `du` over the daemon-reported volume mounts, with a settle loop requiring two readings within 1%. A volume in an image with no `du` is sized from a helper container (BUGS.md F38).
- **IO.** Cumulative `rbytes`/`wbytes` from `io.stat`.
- **Phases.** `build_s`, settle, query generation, ground-truth load, search wall, recall computation, and `phases_accounted_s` so unexplained time is visible rather than absorbed. The dense and sparse lanes also split `ingest_s` from `index_s` where the engine has the boundary. Every lane prints `PHASE` markers as it goes, so a cell killed by its timeout still says which phase it was in.
- **Cold and warm**, separately: the first iteration after the database is opened is the cold number and the remaining iterations are the warm one, on every timed query (DECISIONS #89). A lane where the split does not apply says so instead of leaving a blank.
- **Envelope.** cpuset, memory cap, heap, observed server heap and page cache, `mem_split`, image digest, engine version, engine commit.
- **Thermal.** `host_temp_c_start` and `_end` from the package sensor, `host_throttle_count_start` and `_end` and `host_throttled_ms` from the kernel, on every row since the queue scripts pulled the fix on 2026-09-14 (BUGS.md F45). mini bounces off its thermal ceiling under a long build while the busy cores hold 4.3 GHz, so the power mode stays as the machine ships and each row carries the temperature and the counters as evidence; no protocol change follows.
- **Instrument.** `instrument`, `bench_host`, the per-engine `durability` string read out of the engine, and the canonical answer digest with its readable sample for every deterministic query (PROTOCOL.md section 2).

## 4. Heap and memory caps

**One cap per tier, identical for every engine.** A cap is a ceiling rather than a reservation, so an engine that needs less is unaffected by a tier whose cap is generous. A per-backend cap would be the unfairness the caps exist to prevent.

**One heap per tier, identical for every JVM engine.** ArcadeDB embedded, ArcadeDB server, Neo4j and Elasticsearch all receive the same `{heap}` from one table (`-Xmx`, `NEO4J_server_memory_heap_max__size`, `ES_JAVA_OPTS` respectively). Non-JVM comparators have no equivalent knob, which is why heap sizing is a documented resource-fitting override rather than a per-engine advantage. Two JVM processes are exceptions and run at their own default heap: QuestDB, which `runner.JVM_BACKENDS` lists, so its rows record the tier heap although no heap is passed to its server, and mongot, the search process inside the MongoDB Search image, whose heap nothing sets (section 7, row 30).

**heap = 0.50 x cap, with three exceptions** (`runner.HEAP_BY_SCALE` against `MEM_BY_SCALE`): deep10m at 0.67 (24g in 36g), and the lifecycle tiers lc1m at 0.67 (16g in 24g) and lc10m at 0.86 (24g in 28g). The runner prints this table at startup and marks any deviation.

0.50 is a deliberate split between heap and page cache, not a default nobody revisited. At every tier except deep10m, `peak_anon` sits BELOW the committed heap (4g heap against 2.7 GiB touched at tiny; 8g against 6.1-6.5 GiB at small), so the JVM never needed the heap it already had and raising the ratio would change nothing measurable. The other half of the cap is not idle: it holds the OS page cache for the engine's own files, which the cold/warm split prices at 9-18x for ArcadeDB against 1.0x for engines resident from load.

deep10m sits at 0.67 because a single fp32 dense build peaks well above the 18g that 0.50 would give. The answer was deliberately NOT to grow the envelope until the engine's own build-cache default fitted: no comparator caches its corpus during an index build, so accepting that default means ArcadeDB takes GiB that Qdrant, Milvus, Chroma and LanceDB do not, and then the envelope grows so that it fits, room only one engine gets. The campaign runs the engine's default cache and the tier keeps the 36g/24g envelope it has always had (DECISIONS #52; #56 pins the fp32 multipass arms to the corpus and is disclosed as an override in PROTOCOL.md section 7). The cache policy is recorded on every row as `graph_build_cache_size` and `graph_build_cache_policy`.

## 5. Launching

```sh
export ARCADEDB_WHEEL=<the pinned wheel> ARCADEDB_SERVER_IMAGE=arcadedb-c25:<pin>   # set together, or runner.py refuses
BENCH_ALLOW_DEV=1 bash build_images.sh   # Phase A; without the flag it refuses a pre-release pin, which every commit-pinned wheel is (a stable release's wheel, the 26.10.1 measurement's, builds with BENCH_ALLOW_DEV=0). It installs jpype1==1.7.1 with the wheel (Dockerfile.bench, section 7 row 73); the repo venv needs `uv pip install --python .venv <wheel> jpype1==1.7.1` for the same reason
export ARCADEDB_ENGINE_COMMIT=<pin> BENCH_HOST=mini   # a paper-tier run refuses to start without the host, and without the commit when it runs an ArcadeDB arm
source campaign_env.sh               # the BENCH_* dataset switches for a hand run; no queue script sources it (the generator, `make_2611_stages.py`, and the September scripts export them inline, PROTOCOL section 6)
campaign_env_check                   # asserts every corpus is present
python3 -u runner.py --lanes ... --scale ... --reps 5
```

**The write workloads run twice, once per durability class (DECISIONS #90).**
The class is a property of the cell, not a second measurement inside one, so a
queue script asks for the same cell twice:

```sh
python3 -u runner.py --lanes l1tpc --workloads oltp --scale tpch1 --reps 5                      # relaxed
python3 -u runner.py --lanes l1tpc --workloads oltp --scale tpch1 --reps 5 --durability strict  # strict
```

The same pair for `--lanes l2 --workloads oltp` and `--lanes e2 --workloads
hybrid`. Everything else -- every read workload, every analytics workload, both
vector lanes' ingests, and the lifecycle lane -- runs once, at the relaxed
default. The strict cell writes its own `run_id` (a `_dstrict` suffix), its own
raw artifact, and its own canonical key, so the two never shadow each other;
`fairness_check` F10b fails a write cell that exists in only one class, and the
three engines with no knob (Neo4j, DuckDB, LadybugDB) are exempt because they
run once and declare it.

Rules that have each cost a run:

- Never sync the repo mid-campaign. A `git checkout` reverted a tracked `runs.jsonl` and lost rows; a mid-campaign merge split one lane's rows across two schemas. Sync between stages, never inside one.
- Archive `runs.jsonl` before anything that could touch it.
- Wait loops read the **last** marker line. `STATUS.txt` is append-only, so a bare grep finds this morning's ABORT and acts on it.
- Kill the process group, not the script: `kill -- -PGID`, then verify with `docker ps` and `pgrep`.
- Never edit a queue script that is running. Bash reads by byte offset, so a mid-run edit resumes mid-token.
- Monitoring is the session's own watch on `STATUS.txt` and `docker ps` on the bench host, through `.notes/bench/mini_watch.sh` (heartbeat, row freshness, ALL-DONE/ABORT/START/OOM/failed cells, dead workers, lost contact).

## 6. The live chain

Finished scripts move to `~/queue_archive` on mini. The chain holds its pin start to finish; an upstream fix landing mid-run becomes a candidate for the next re-pin, never a restart.

**Sizes, every campaign (#108).** Each table carries two sizes wherever a second one is affordable and informative: graph interactive SF1 and SF10, documents transactional and analytical TPC-H SF1 and SF10, time series 100 and 1,000 hosts, cross-model 50k and 500k products, dense 1M and 9.99M, sparse 100k / 1M / 8.84M. Graph analytics is the single exception at one size, the full SF1 network, because the full network at SF10 is not feasible. Plan the matrix at two sizes from the start; if it does not fit, the transactional documents table's SF10 is the first size to drop, and dropping it is recorded rather than done silently.

**The cap rule (DECISIONS #188, 2026-10-18).** Stated in full in PROTOCOL.md section 2 and implemented by `cap_rule.py`. `make_2611_stages.py` lowers each cap and seeds the skip from `cap_rule_2610.json` at run time, and `export_web.py` applies the rule to every row at report time.

Rules every campaign keeps:

**Every page table needs a stage that produces it** (BUGS F84). Before a campaign, walk the payload's table list and name the stage that feeds each one: the e4 decomposition had none, because `export_web` refuses a page without `e4decomp_<pin>` and September's artifact was made by hand. `make_2611_stages.check_coverage()` proves it for every registered arm of every page lane the generator stages; a lane it does not stage (the e4 decomposition, the restart lane) needs a stage of its own before a page can read it.

**Every stage checks that its images carry their pins before it runs (BUGS F90, F76).** "Images present" is true of an image built a week before the pin moved: `dbbench:pg-age` sat on PostgreSQL 17.11 under an instrument pinned to 18.6 for nine days, and AGE 1.8.0 builds edges about 65x faster than 1.7.0, so the cross-model cell at `e2_500k` spent its entire 7,200 s cap on edge creation and was recorded as a censoring that reads like an engine limit. The ArcadeDB arm is verified by content (`verify_pair_c25.sh` reads the jar's own build number), and `version_pin_check --runtime` gives every comparator the same treatment: it runs each `dbbench:*` image and reads its versions back out before cell 1. An image that is absent, or that cannot state its versions, is a failure and not a pass; pins it cannot resolve (`PKGS[arcadedb]` is a shell variable) are reported rather than skipped silently.

**Every stage checks that its whole cell fits before it runs (BUGS F74, #109).** The budget sum bounds what ITERATIONS may cost; it cannot see a query's FIRST TOUCH, which #82b makes always complete, and one query spent 1,384 s on its first touch alone while its budgets summed to 48% of the cap. Each stage runs `cell_cost_check` for every tier it will use (ingest plus measured first touches plus the budget ceiling, against the cap) and aborts only on a SCORED projection over the cap. A tier whose query roster has no rows yet is reported and not blocked, because the tool refuses to score what it cannot see rather than guessing (it once scored 5 of 14 queries and reported ok).

**Every stage with a timed write runs it twice, once at each durability class (#90, FAIRNESS F10b).** `make_2611_stages.STRICT_WORKLOADS` (derived from `fairness_check.WRITE_CELLS`) names the three (lane, workload) pairs that get the second pass: documents and graph `oltp`, and cross-model `hybrid`; `atomicity` is not a timed write and stays at one class. Reads are untouched and bulk ingest stays at one setting (#90a). THE CLASS IS A CLI FLAG, NOT AN ENVIRONMENT VARIABLE: `runner.py` assigns `os.environ["BENCH_DURABILITY"]` from `--durability`, default `relaxed`, so exporting the variable is overwritten before any lane reads it and the cell runs relaxed while claiming nothing (BUGS F81).

**A repair runs directly after the stage it repairs**, not behind the long stages queued after it: a repair queued behind them leaves its table unlandable for all of them, and the campaign is sequenced by uncertainty, where an arm known to be broken is the most certain thing on the board to fix. A repair is a new stage at the tail, never an edit of a running one (section 5 says why).

**A stage builds the images its backends name (#110).** `_images_for()` reads `image` and `server_image` off each backend in `runner.BACKENDS`, so a new arm brings its image with it; the stage then verifies each one exists before the first cell. The typed list this replaced had gone stale in three places at once, and none of the three announced itself as a missing image: MongoDB's arm reported `server_not_ready`, which reads like a slow engine.

## 7. The re-pin checklist, and the rules a campaign taught

**A new ArcadeDB release replaces the old one until the final DBBench release (DECISIONS #189).** When the new version's ArcadeDB pass has landed: run ONE scripted comparison of the old and new ArcadeDB rows (a regression worth filing before the next cut is the only use left for the old rows); then remove the old version's ArcadeDB rows, page data, pin-specific code paths, pinned test fixtures, wording, jars, wheels and images; the raw old rows stay only in mini's `~/queue_archive` until the paper is submitted. Comparator rows are kept, in a set that names no ArcadeDB version. A running chain is never relabelled for this (every stage pulls main at its start). Bindings release history and engine code are out of scope. After the final release, a new version adds rows and the page keeps the history (PAGE-SPEC.md section 1).

**The re-pin checklist: everything a measurement owes the harness, not just the engine.** This is the ONE list of re-pin changes; HANDOFF points here rather than keeping a copy. Each row names the decision behind it. A row that is built and verified is condensed to a line that keeps its number, because code comments, tests, and DECISIONS cite rows by number: never renumber, reorder, or delete one. An open row, or one that carries an instruction a future run needs, stays whole. Nothing on the list changes a running chain, because a mid-run change splits the rows; every item is settled before the first cell of the next measurement (step 1 of the routine). An item that moves ArcadeDB's numbers is the user's call (the "free for them, decisive for us" rule). Once decided, an item becomes a DECISIONS entry naming what it amends or retires, changes PROTOCOL.md, FAIRNESS.md, and the method pages in the same commit, and is condensed here once built. **Scope** says whose numbers an item moves: ArcadeDB's alone, or comparators too, which then need re-measuring with it.

The default order is the core block first, then the second list. Splitting moves stage boundaries only, and `--check` proves the cells are the same. `--project TABLE` prints projected hours per drafted stage from a per-cell hours table (tab separated: lane, workload, scale, backend, class, hours at 3 repetitions, hours at 5 repetitions; a cell with no clean rep carries its one failed attempt). `--check --drafts DIR` lints written scripts: the instrument exported and never 2026-10, the 2611 rows file, only subset arms, each stage waiting for the one before it. Drafts are written to a folder outside the tree and copied to the bench host by hand on the owner's go. **What a stage costs is projected from its components, never from an uplift.** Multiplying the previous campaign's cells by an assumed per-lane uplift goes wrong in both directions: a larger query set lengthens a stage several times over, and a stage that runs fewer workloads than the cells it is priced from runs shorter. Project each cell from its measured ingest, first touches, and budget ceiling, as `cell_cost_check` does, and replace a stage's projection with its measured cost once it runs. The current projection lives in HANDOFF.

**The chain is ordered by priority across tiers and by uncertainty inside one.** Inside a tier, a stage whose figure is the only projection on the board, or whose size an open diagnosis can block, runs early, so a wrong figure is found on day three rather than day thirteen; the well-characterised long stages run late, and the largest runs after the others, so every other table lands before it and an error in it costs no other table.

**Before launching, check that every `budgets.py` key names a (lane, tier, query) a lane asks for**, since a name mismatch silently falls back to the lane's constant on every query. A new instrument's queries mostly run on the constant by design: the row records which of the two applied, and step 7 of the per-campaign list regenerates the table from the campaign's own rows.

**One freeze, landed stage by stage.** The campaign's rows accumulate in their own per-pin file (`runs_page_<pin>_2611.jsonl`) and land table by table into the one freeze through `land_stage.py`; every landing runs every gate and renders 2026-11 rows only, and the lane pages show a table once its rows are frozen and declare the others pending (`pending_tables`). When the freeze is complete and every gate is green, the page and the results asset are published from that freeze (PUBLISHING.md).

## 8. Filing an engine weakness upstream, as a routine

The maintainers want the losses: a benchmark that finds a weakness and says nothing has done half the work. The comparison is CURRENT ArcadeDB against the OTHER ENGINES, never ArcadeDB against its own past versions; a cross-version difference in our own rows is a question about our page and belongs to the landing checklist, not to their tracker.

**Step 0, after every landing: `python memo_bottlenecks.py --triage`.** It reads the payload the landings write (`results/web_benchmarks.json`) and, within each scale, ranks every published cell by how far ArcadeDB trails the BEST comparator in that column; the header names the payload and the ArcadeDB commit. **A gap is a place to LOOK, never a finding.**

1. **Audit the harness before the engine.** Is the arm on the pin, on the documented bulk path, matched by effect (index, durability class, corpus), and is the metric even comparable (memory especially)?
2. **Reproduce it small, on a real filesystem.** `/tmp` is tmpfs on both hosts, so an fsync there is a no-op.
3. **Find the control that isolates the trigger.** It separates a filable issue from an anecdote.
4. **Write the repro in Java**, one file, compiled against the image's own `lib/*`, with no dependency beyond the engine jars.
5. **Run it on two builds**: a published release and the current `-SNAPSHOT`, so it is not already fixed.
6. **Read their tracker first**, for the symptom and the mechanism; rule out near-misses in the issue body, and comment on a closed duplicate instead of posting one.
7. **Claim only what was measured.** Say plainly what was not run (a kill-test, for instance).
   - 7b. Suggest a fix only where there are grounds: point at the code you read, say what you did not verify, and offer alternatives rather than a verdict. Where the mechanism is not understood, say so and stop.
   - 7c. Ask, not only report: where ArcadeDB ranks low and the harness might not use it the best way, open a question with the metric, the rank, and the exact Java, SQL, or Cypher the lane runs.
