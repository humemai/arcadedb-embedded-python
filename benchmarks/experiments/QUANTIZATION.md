# What each vector engine ships, and what the page runs

The quantization survey of DECISIONS #131 item 8 (CAMPAIGN.md section 7 row 42), taken 2026-10-02 against the pins the 26.10.1 measurement starts from. For every dense and sparse comparator: the representations its pinned image ships, what our DDL builds today, and whether it gets an int8 arm. The rule is DECISIONS #53, extended to the sparse table by #131: an engine that ships an int8 (or int8-class) mode gets an int8 arm beside its full-precision one, at the same operating point, and each row records the representation it ran as `quantization`.

**Source column.** "image" means checked on the pinned image or client package on 2026-10-02 (the probe is named); "docs" means the engine's documentation for the pinned version, not yet run here; "adapter" means what our own DDL issues; "smoke" means the arm ran through the runner on the laptop at the named scale, against the pinned image, and its row carries the representation the engine reported (laptop rows prove the arm runs and what it built; they are not measurements).

**Status, 2026-10-02.** Every int8 arm the survey owed is built: each sets its representation in the index definition, reads the applied one back from the engine onto the row, and refuses the cell on a mismatch (BUGS F164: a declared quantization is a claim, the read-back is evidence). Recall@10 below is from the laptop smoke against exact ground truth (dense: SIFT, 5,000 and 20,000 vectors; sparse: the 5,000-document synthetic corpus and the 100,000-document Big-ANN SPLADE slice), fp32 arm first, at the same operating point.

## PQ arms (the 2026-11 instrument)

Product quantization is a fourth representation beside fp32, int8 and the engines' binary modes, and it gets its own row family, labelled "pq" on the page. The arms exist only when `BENCH_DENSE_PQ=1` is set (`bench_common.dense_pq_enabled`), so a stage starts no PQ cell by accident, and the page prints a PQ row only when it carries instrument 2026-11. They stay off until the measured ArcadeDB release carries the upstream PQ fix (ArcadeData/arcadedb#10545, merged 2026-10-21 for 26.11.1, which carries #10516 to #10519; it also makes the re-rank candidate count the index setting `rerankOversample`, default 10, and keeps the per-query `rerank` option of `vectorNeighbors`): before it ArcadeDB's SQL search ignores a PRODUCT index, so the ArcadeDB arms probe the `rerank` option of `vectorNeighbors` at connect and refuse to run on a build that rejects it, rather than measure exact search under a PQ label.

One PQ setting for the family, matched as closely as each engine allows: 32 subspaces (`BENCH_DENSE_PQ_SUBSPACES`, which must divide the dimension) of 256 centroids (8 bits), so a 128-d SIFT vector is 32 bytes of codes. ArcadeDB sets `pqSubspaces` and `pqClusters` explicitly. Qdrant takes a compression ratio and fixes 256 centroids per chunk, so x16 is 32 subspaces. Milvus takes `m` and `nbits`. ArangoDB takes the FAISS factory string. Where an engine can re-rank the PQ candidates on the stored floats, it does, at 10 candidates per requested neighbour (ArcadeDB's own default, Qdrant `oversampling`, Milvus `refine_k`); ArangoDB's factory has no re-rank stage and says so on its row (`pq_rerank`). Every row records `pq_subspaces`, `pq_clusters` and `pq_rerank`, the engine's read-back of the index it built, recall@10 against the same exact ground truth, the build time, and the index size (the cell's `disk_data_mb`, plus `pq_index_bytes` for embedded ArcadeDB and `ivf_index_bytes` for ArangoDB).

LanceDB has an `IVF_HNSW_PQ` index but no arm: it trains one codebook per IVF partition, not over the corpus, which is a different PQ setting from the other four, so its fp32 and SQ arms stay its comparison.

Smoke, 2026-10-21, laptop, the first 5,000 siftsmall vectors and 80 timed queries, recall@10 against exact ground truth; these prove the arms build, read back what they built and answer, they are not measurements. ArcadeDB embedded on an engine build with the PRODUCT search (ArcadeData/arcadedb#10518, built locally): recall 1.0, build 21.4 s, 7.0 MB of index files. Qdrant: recall 1.0, but 5,000 points is below its indexing threshold (10,000), so the answer came from a scan and the smoke proves only the build and the `product x16` read-back. Milvus `HNSW_PQ` (read back with `m` 32, `nbits` 8, `refine` FP32): recall 1.0, build 14.7 s. ArangoDB and the served ArcadeDB arm: smoke pending (the served arm needs a server image that carries #10518; ArangoDB's container waited on the laptop's shared heavy-job slot).

## The beam sweep and the precision arms

Under the 2026-11 instrument the dense lane sweeps the search beam on the built index and headlines latency at matched recall (PROTOCOL.md section 2). Precision arms change nothing in that rule: each int8 and PQ arm is swept over the same `ef` list as its fp32 sibling (ArangoDB's over `nProbe` around its calibrated value), and the re-rank settings stay as the arm set them (Qdrant `oversampling`, Milvus `refine_k`, ArcadeDB's engine default, none for ArangoDB's factory string), so a quantized arm's curve is the beam sweep at its own fixed re-rank. A quantized arm that does not reach the target at the top of the list is marked `not reached`, which is how a coarse code shows up in the headline.
